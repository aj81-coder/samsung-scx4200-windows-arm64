# Decoded raster capture implementation notes

Current status: capture-only development handoff prepared after native builds and eight x64 integration checks. See VALIDATION.md. The initial audit below identifies the original upstream behaviour; generated adaptations now address original header allocation limits, callback failure propagation, raster input budget and truncated subsequent headers. Other listed reliability and target checks remain outstanding.

Validation so far: source compiled to an x64 object with Zig 0.15.2, C11, `-Wall -Wextra -Werror`, against the pinned CUPS 2.4.11/PAPPL 1.4.10 public headers. Linking, runtime, and ARM64 target execution remain separate checks.

`capture.c` uses PAPPL 1.4.10 callbacks and Windows BCrypt SHA-256. Link bcrypt. It creates a new timestamp/process directory, binds only `127.0.0.1:8631`, disables DNS-SD names and TLS, runs in the foreground, and never enumerates or opens USB devices. A custom local device scheme refuses all device writes. No service, subprocess, queue or default-printer changes are made by the application.

The driver advertises A4, simplex, monochrome sGray 8-bit, 300 dpi. It retains **decoded callback rows**, not the original submitted PWG/URF document. Each page gets a `.rows` binary, JSON with callback dimensions/layout, document MIME type and SHA-256, and a framework log. Source pixel polarity is defined by the recorded CUPS color-space number: sGray (18) is 0 black/255 white, K (3) is 0 white/255 black. Callback data can have been transformed/padded by PAPPL. JSON explicitly means completion of a page callback, not physical output or proof the entire submitted document was valid.

Output bounds: 3,600 pixels per dimension, one byte per pixel, 10 pages per job, 128 MiB of attempted decoded row writes per process (including failed jobs). Page dimensions/layout checked before this application creates a page file; row order and sizes checked on every callback. Partial output remains `.partial`. Existing files are never overwritten. A fresh run directory is required for additional quota. SHA-256 is streamed without page-sized allocations. Filesystem failure latches a failure which end-page/end-job callbacks propagate.

## Framework issues requiring primary integration work

1. `job-ipp.c:_papplJobCopyDocumentData` routes PWG/URF directly through `job-process.c:_papplJobProcessRaster`. It does not call the raw-file callback or MIME filter. Consequently the public callbacks cannot retain original on-wire bytes.
2. Generic non-raster documents are spooled in an unbounded HTTP read/write loop before driver callbacks. `papplSystemSetMaxImageSize` limits image decoding, not HTTP bodies/spool consumption. `papplPrinterSetMaxActiveJobs` limits count, not bytes. The application’s decoded-output quota does **not** bound framework spool data. This remains a handoff blocker until the framework path is bounded or non-raster input is rejected before spooling.
3. `printer-driver.c:make_attrs` automatically adds octet-stream, PWG, URF, plus compiled image filters. Driver extra attributes are appended via `ippCopyAttributes`, so adding a second `document-format-supported` does not reliably narrow the list. Do not claim a PWG-only endpoint without checking the actual negotiated attributes and acceptance behavior. The callback only accepts PWG/URF but rejection after spooling is insufficient for a spool bound.
4. Raster callbacks receive `options->header`. The framework only copies the original header here when source and output have >=8 bits/pixel. Malicious 1-bit input can therefore have different dimensions from those checked by our callback before framework pixel allocation. The decoder and framework input-header dimensions, row byte multiplication/overflow, total bytes/pages and quotas need separate guards. Advertising sGray alone is not input validation.
5. PAPPL 1.4.10 ignores return values from `rwriteline_cb`; therefore errors are latched and end-page returns false. The framework also pads/discards lines and may not distinguish EOF at a complete page boundary from a truncated next header. Page callback completion must not be treated as wire-document validation. Keep these acceptance checks explicit.
6. Need runtime verification that NULL DNS-SD names suppress all discovery, listener is exactly IPv4 loopback, actual printer URI is `/ipp/print`, no unwanted TLS/default listeners appear, cancellation/disk-failure semantics work, and the Windows IPP class queue accepts the advertised printer. No target ARM64 execution claimed yet.

Useful tests before handoff: real Get-Printer-Attributes and Print-Job; one/two-page controlled PWG fixtures; verify decoded pixels and hashes; URF if advertised; chunked HTTP and size rejection; malformed header/oversized dimensions/row multiplication; truncation inside page and next header; canceled job; occupied listener; unwritable/full disk; process restart preserving previous captures. Obtain final job-state evidence separately from page JSON.

## Restricted generated framework sources

`prepare-capture-guards.ps1 -PapplSource <pinned PAPPL root> -OutputDirectory <generated directory>` hashes both original source files, asserts exact anchors and writes only generated `job-ipp.c` and `job-process.c`. It refuses output within the upstream tree. Both generated files compiled to x64 objects using the integration build's generated config and CUPS/PAPPL include paths.

The guards reject non-PWG/URF before generic disk spooling, validate the original raster header before PAPPL options/row allocation (8-bit one-channel chunky sGray/K, 300 dpi, nonzero <=3600 dimensions, row bytes equal width), limit each job to ten pages, remove dither/padding/discard behavior for this restricted capture build, and propagate short row reads/callback failure as an aborted job. These generated files must replace the corresponding originals in the build; just running the script does not activate them. Error handling uses existing PAPPL IPP response and cleanup labels.

Remaining resource boundary: **CUPS 2.4.11 allocates its compressed-row buffer inside `cupsRasterReadHeader`, before PAPPL can validate the returned header.** `raster-stream.c` calls `cups_raster_update` near line725; that helper allocates `cupsBytesPerLine` near line1676. A separate CUPS pre-allocation guard is still needed. The patched PAPPL function also uses existing HTTP flush/drain cleanup, which has no total transport-byte budget. Neither this script nor the application claims a strict HTTP input bound. EOF at a page boundary versus a truncated next header remains a decoder-level validation issue. Advertised format capability list still needs checking against the restricted acceptance list. These remain explicit test/integration requirements, not evidence of readiness for untrusted requests.
