# Windows cancellation diagnostic

This is a controls-only diagnostic for the existing bridge. It requires Windows PowerShell 5.1, PrintManagement, and the adjacent `cancel-current-job.ps1`. The source-tree fallback imports that same helper from `../native-reliable-bridge` for tests. The helper's executable/path/listener ownership checks remain in force when packaged beside the production executable.

Only one action changes printer state: `Remove-PrintJob -PrinterName 'SCX-4200 Capture Test' -ID <recorded Windows job ID>`. It is attempted at most once. The script itself sends only IPP Get-Jobs (10) and Get-Job-Attributes (9). It never calls the imported direct IPP cancellation function. A Windows queue row disappearing is not evidence that IPP cancellation arrived. An observed remote state 7 is recorded separately; the bridge framework log remains the authoritative request trace.

Selection requires empty Windows and remote active-job baselines, exactly one new Windows job, and exactly one new active bridge job. Their IDs are independent. The Windows ID plus SubmittedTime are checked repeatedly to guard reuse. Bridge PID/start time/path, exclusive loopback listener, queue/port/driver configuration, and spooler PID/start time must remain unchanged. Multiple jobs, terminal/deleting/printed status, restarted jobs, unknown status flags, or missing submission timestamps prevent cancellation. A second set of identity and Windows job checks follows the final remote query immediately before the action. No separate Windows/IPP API offers an atomic cross-system association; this diagnostic depends on the instructed one-document, empty-baseline run and records the identities it actually observed.

Windows status flags match the installed PrintManagement CDXML `MSFT_PrintJob_v1.0.cdxml`. Terminal mask is 0x1184 (Deleting, Printed, Deleted, Complete). The known flags mask is 0x7fff; Restarted is separately refused. The known textual enum forms are also checked if numeric conversion fails.

The monitor polls Windows about every 250 ms and remote jobs about every second. It waits 10 seconds after observing remote processing, attempts Windows cancellation only while that same Windows job remains live, and then observes for 20 seconds. Acquisition expires after 120 seconds; a 175-second outer loop cap also applies. IPP helper HTTP calls each have a 5-second timeout. These are monitoring bounds, not a guarantee against a Windows management cmdlet itself hanging inside the operating system. No process kill, service restart, queue creation/deletion, USB reset, second print, automatic replay, or administrator prompt is used.

The JSONL trace flushes each transition and the final JSON summarizes IDs, sanitized queue/driver information, status, exact action timestamps, and remote observations. Titles, usernames, port names/addresses, executable paths, and raw exception messages are omitted. The printer may still contain buffered data after any cancellation.

`test-windows-cancel-diagnostic.ps1` uses only mocked local queue, identity, clock, IPP, and removal operations. It runs under Windows PowerShell 5.1 without Python. The 25 scenarios verify forwarded cancellation, unforwarded cancellation despite local disappearance, failed removal without retry, pending baselines, ambiguous jobs, changed job/bridge/queue/spooler identity, ID reuse, unusable timestamps/status, numeric and textual restarted status, terminal states, final pre-action changes, and acquisition timeout. Test evidence is written to `build/windows-cancel-diagnostic/test-results.json` with the exact script SHA256. No real queue mutation, network request, or USB operation occurs in those tests.
